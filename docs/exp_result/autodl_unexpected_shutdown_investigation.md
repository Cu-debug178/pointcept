# AutoDL 意外关机调查记录

## 2026-07-13 关机的已确认根因

2026-07-13 13:32 的关机由一次错误的诊断命令直接触发。此前的
Codex 会话为了检查关机命令是否可用，执行了：

```bash
/usr/bin/shutdown --help
```

AutoDL 镜像中的 `/usr/bin/shutdown` 不是标准 systemd 命令，而是一个
忽略所有参数的包装脚本。即使传入 `--help` 或 `--show`，它仍会杀死
`supervisord`，从而关闭容器。该文件记录的访问时间是
`2026-07-13 13:32:26.789 +0800`，与评估日志和 GPU 遥测同时中断的时间
完全一致。

关机前 0.3 秒的进程快照显示评估主进程以及两个关机 watcher 都仍然
存活；watcher 日志也没有出现 `watched_process_stopped` 或
`requesting_shutdown`。因此这次不是 watcher 正常触发，而是
`shutdown --help` 本身触发。

同时确认了第二个设计缺陷：工作区曾创建多个脱离终端运行的 watcher，
其中一个会在任务失败或没有退出码时无条件关机。这些入口已经删除；
活动仓库的 shell 入口由 `tests/test_no_auto_poweroff.py` 检查，并覆盖
`/usr/bin/shutdown` 这类绝对路径调用。

### 后续规则

- 不在 AutoDL 容器中执行 `shutdown` 的任何变体，包括 `--help`、
  `--show` 和 `-c`。
- 任务结束只写退出码和日志，不从训练或评估脚本操作实例电源。
- 需要停止实例时只使用 AutoDL 控制台，由用户明确操作。
- 不创建脱离终端的关机 watcher，也不在异常退出路径中关机。

## 结论

2026-07-10 13:53 的关机最可能由此前已经启动的历史包装进程触发，而不是固定协议评估、GPU 负载或诊断命令触发。历史脚本会在任务成功或失败后等待 300 秒并执行系统关机；更新或删除磁盘上的脚本不会改变已经运行在内存中的 Bash 进程。

结论置信度：中高。现有日志没有保存到执行关机命令的最后一行，因此不能标记为完全确认；但提交时间、旧脚本行为和日志截断时间相互吻合。

## 已确认事实

- `e5a5b0c` 在 2026-07-10 12:55:29 添加了 `run_fixed_screen_then_shutdown.sh`。
- 该历史脚本无论评估成功或失败，都会等待 300 秒后执行关机。
- 诊断日志创建于 2026-07-10 13:53:39，只写入时间和主机名，随后被截断。
- 删除历史关机入口的提交 `e85f63f` 创建于 2026-07-10 13:58:29，比该次关机晚约 5 分钟。
- 诊断日志被截断时，固定协议 Python 评估尚未开始。
- 当前分支 `fa74777` 之后的复评代码没有主动关机命令。

## 因果链

```text
旧版本复评快速失败
-> 历史包装脚本进入 300 秒等待
-> 工作区随后 git pull 到新版本
-> 已运行的旧 Bash 进程不受文件更新影响
-> 倒计时结束并关闭实例
-> 同时运行的诊断日志在 hostname 后被截断
```

## 仍需排除的外部原因

- AutoDL 控制台配置的自动停止或预算策略。
- `/root/.bashrc`、cron、systemd timer 中的用户自定义任务。
- 另一台独立服务器上仍在运行的同类历史包装进程。

新安全启动器会在启动前停止历史包装进程，并持续写入心跳和退出码。若再次发生实例停止且没有 `.exit` 文件，则应把原因升级为 AutoDL 平台或系统级任务，而不是 Pointcept 复评代码。
